# From a CDK financial event to an ACDOCA-shaped line

This document walks one concrete event — a closed CDK repair order — through to the
ACDOCA-shaped row(s) it produces on the sovereign spine, column by column, and marks
which columns are sourced, which are derived, and which are null because a DMS has no
equivalent. See [`mapping.md`](mapping.md) for the object-level crosswalk this projection
draws on, and [EgD-CDK-FIELDS-v2](https://github.com/EVEglyphDesign/eve-hawkins-cdk-twin)
(`docs/model/fields.json`) for the upstream field contract.

## The event

A `repair-order` (CDK) closes with one `ro-labour-line` and one `ro-part-line` attached.
In SAP terms this is an internal order (`AUFK`) accumulating actual costs (`COSS`/`COSP`)
that settle to a cost center (`CSKS`) at period end. On a real S/4 system, settlement
posts a document that becomes one or more `ACDOCA` rows. CDK has no settlement run and no
`ACDOCA` table — this projection is what stands in for that posting.

## Column-by-column projection

| ACDOCA column | Meaning | Source | Sourcing |
|---|---|---|---|
| `RCLNT` | Client | Fixed value for the sovereign tenant, not from CDK | derived |
| `RBUKRS` | Company code | `dealer-rooftop-partition` — the rooftop the repair order was opened at | sourced (partial API) |
| `BELNR` | Accounting document number | Generated by the spine at ingestion time — CDK has no SAP document-number concept | derived |
| `GJAHR` | Fiscal year | Derived from the repair order's close date | derived |
| `BUDAT` | Posting date | `repair-order` close date / `gl-journal-posting` `BKPF-BUDAT` if a journal event exists | sourced (full or partial API, depending which layer fires first) |
| `BLART` | Document type | Mapped from CDK transaction type to an internal convention (e.g. "closed RO" → document type `SV`) | derived |
| `RACCT` | G/L account | `gl-account-master` `SKA1-SAKNR`, resolved from the labour/parts cost element via `CSKB` | sourced — **but `gl-account-master` has no API reach; this column depends on a file/export extract, not a live pull** |
| `KOSTL` | Cost center | `cost-centre-department` → `CSKS`/`CSKT` — the department the repair order's cost element settles to | sourced — **no API reach; file/export only** |
| `AUFNR` | Order number | `repair-order` → `AUFK-AUFNR`, the CDK repair-order number carried through unchanged | sourced (full API) |
| `KUNNR` | Customer | `customer-master` → `KNA1-KUNNR`, present only on the revenue side (if the repair order is customer-pay, not warranty or internal) | sourced (full API), conditional |
| `LIFNR` | Vendor | Only populated if the order includes a sublet line — `vendor-master` → `LFA1-LIFNR` | sourced — **no API reach; file/export only**, conditional |
| `HSL` | Amount in local currency | Sum of `ro-labour-line` (rate × hours) and `ro-part-line` (moving-average cost × quantity) | derived (computed from two sourced lines, not copied from a single field) |
| `KSL` | Amount in controlling-area currency | Same as `HSL` unless the dealer's functional currency differs from the controlling-area currency, in which case it is a currency-converted derivation | derived |
| `MEINH` / `MENGE` | Unit of measure / quantity | `ro-part-line` quantity fields, where the line is a parts consumption rather than a labour hour | sourced (full API) |
| `SGTXT` | Line text | Repair-order description / complaint text, truncated to ACDOCA's line-text length | sourced (full API) |
| `PRCTR` | Profit center | **Null.** CDK Drive has no profit-center concept distinct from cost center/department; a dealer group with one rooftop per company code has no need for a second profitability axis, and this spine does not fabricate one | **null — no DMS equivalent** |
| `SEGMENT` | Segment (segmental reporting) | **Null**, same reasoning as `PRCTR` — no CDK equivalent | **null — no DMS equivalent** |
| `PSPNR` | WBS element | **Null.** No project system concept in CDK; a repair order is not project-costed | **null — no DMS equivalent** |
| `VBUND` / `PARGB` | Trading partner / partner business area | **Null.** A single-entity dealer group has no intercompany trading partner to record | **null — no DMS equivalent** |

## Where the ESG score and interaction-record extensions attach

Per this repository's [ESG/ACDOCA extension doctrine](../../../docs/DOCTRINE-ESG-ACDOCA-EXTENSION.md),
every ACDOCA-shaped line can carry an appended ESG score and an interaction-record
pointer without touching SAP's own reserved column space. For a CDK-sourced line:

- **ESG score** attaches at the `repair-order` level, not the individual labour/parts
  line — e.g., a repair order that includes an EV-specific service or a warranty repair
  that extends a vehicle's service life scores differently than routine maintenance. The
  score is computed once per settled order and carried on every ACDOCA line that order
  produces.
- **Interaction-record pointer** attaches at the same grain as `SGTXT` — it references
  back to the originating CDK `repair-order` ID (and, where present, the `warranty-claim`
  ID) so a human or an auditor can walk from an ACDOCA line back to the dealer-floor
  record that produced it. This is the mechanism that keeps the "same business fact, same
  identity" rule honest end to end, per the [symmetric-alignment doctrine](../../../docs/DOCTRINE-SYMMETRIC-ALIGNMENT.md).

Both extensions are appended, not interleaved with native ACDOCA columns — a system that
only understands standard ACDOCA can ignore them entirely and still read a correct line.

## What this projection does not claim

It does not claim CDK Drive will one day expose a native settlement run, a profit-center
axis, or a WBS concept — it won't, because CDK is not SAP and was never meant to be. The
null columns above are permanent nulls for this feeder, not gaps awaiting a future API
version. That is the honest shape of a non-SAP feeder, and it is asserted here rather than
padded with invented values to make the row look more complete than the source system is.
