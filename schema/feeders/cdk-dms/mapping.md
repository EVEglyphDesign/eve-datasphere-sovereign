# CDK Drive → SAP table → ACDOCA line — object crosswalk

Source of truth for the left-hand column: [EgD-CDK-FIELDS-v2](https://github.com/EVEglyphDesign/eve-hawkins-cdk-twin),
`docs/model/fields.json` (21 entities, 443 fields, generated 2026-07-29). Source of truth
for the middle column: `schema/sap-modules/*/tables/*.yaml` in this repository. Where the
middle-column table is not yet field-level defined here, that is stated rather than
assumed closed — see the [reconciliation note](../../sap-modules/RECONCILIATION-NOTE.md).

Confidence follows the same three marks used across this canon: **DOCUMENTED** (the CDK
twin's contract states the analogue and this repo has the SAP table defined),
**INFERRED** (a reasonable analogue with no formal SAP object behind it), **UNVERIFIED**
(asserted, not yet checked against a live extract).

## What this table is not

It is not a claim that every row above has been proven against a live extract — the
[EgD-CDK-FIELDS-v2 contract](https://github.com/EVEglyphDesign/eve-hawkins-cdk-twin) itself
marks most `sap_field` values `INFERRED` because CDK Drive predates any SAP mapping
exercise and its object model was never designed against SAP's. What this table is: the
single place that states, honestly and per object, what the analogue is believed to be,
how confident that belief is, and whether the API can reach it at all — so that when the
CDK admin login lands, an extract job has somewhere to look up where each field belongs
without a human re-deciding it field by field.
